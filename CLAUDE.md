# da Cecot Food — Identity Card

Custom **static** rebuild of dacecotfood.com (authentic Italian comfort-food pasta bar & street-food kitchen, Edmonton AB). Client project for **Unconventional Group**. This is the dacecot site — NOT a framework app, NOT another caterer.

## What it is / who it's for
- 13-page marketing site for da Cecot Food Inc. Production-ready: full SEO/AIO, structured data, responsive, accessible.
- Pages: home, menu, about/our-story, experiences (hub) + 5 sub-pages (sunday-pasta-classes, pasta-drop-in / pasta-shop, food-drink-experiences, private-events, catering), events, reservations, contact/visit-us, partnerships. (On-disk filenames include `our-story.html`, `pasta-shop.html`, `visit-us.html` — README lists older slugs; trust the generator output.) Plus `404.html`, `sitemap.xml`, `robots.txt`, `favicon.svg`.

## Brand / design system
- cream **#f9f7ef**, brown **#4a1e18**, olive **#374225**, terracotta **#ad5217**, gold **#c4a035**.
- **Playfair Display** (headings) + **Inter** (body). Experiences dropdown nav, FAQ accordions, alternating sections.
- dacecotfood.com itself is the quality bar referenced for other UGroup builds.

## Tech stack
- Plain static HTML/CSS/vanilla JS, NO runtime framework. Pages are **generated by a Node build script** — do NOT hand-edit the `.html` files (overwritten on build).
  - `.claude/build.js` — head/SEO, nav (Experiences dropdown), footer, schema helpers + the 7 core pages.
  - `.claude/build-experiences.js` — the 6 Experiences pages + final writer (sitemap, robots, 404, favicon, CSS minification).
- `css/styles.css` (source) → `css/styles.min.css` (generated, linked by pages). `js/main.js` = mobile nav, dropdown, FAQ accordion, scroll reveal, back-to-top, forms.

## Build
- `node .claude/build.js` regenerates all 13 pages + 404 + sitemap + robots + favicon + styles.min.css. **Edit the generator, then re-run** — editing `.html` directly gets overwritten.
- **Gate: `npm run gate`** (`npm test` → `npm run build`). Green before any claim of done. `npm test` runs `classes` (schedule, push planner, send.js confirmation emails), `closures` (one-off closures — including the server half, which is the half a browser check cannot cover), `no-reservations` (days open but with no online table bookings — and that pickups still run), `pause`, `pricing`, `followup`, `cms-store` (what the admin is told when a GitHub save fails, and the pre-flight that warns first) and `build-output`, which runs the real build and asserts on the generated HTML rather than on the generator.
- Beyond the static site there is a runtime layer: `api/` (Vercel serverless — **10 of the Hobby cap of 12**, so add actions to an existing handler rather than new files), `lib/orders` (Neon-backed submissions store + Resend mailer), `lib/cms` (content store/auth), `lib/classes` (class schedule + push planner) and `admin/` (Erika's site manager at `/admin`). Content lives in `content.json`, committed via the GitHub backend, so editing it IS editing live content.

## SEO / AIO
- Unique title/meta/canonical/OG/Twitter per page; one `<h1>` each; semantic structure; alt text + lazy/async images.
- JSON-LD: Restaurant (home), Restaurant+LocalBusiness (contact), Event (classes/drop-in), Service (experiences/private-events/catering), FAQPage, BreadcrumbList. "What is…" answer paragraphs + FAQ accordions for AI Overviews.

## PLACEHOLDERS / gotchas
- **Images** sourced from the client's Wix CDN (live-site real photos). The client's Google Drive originals folder is **private/download-locked (403)** — can't auto-import; see `DRIVE-PHOTOS.md` for filename/ID inventory + the access issue.
- The **contact form** (visit-us) is a front-end mockup (FormSubmit, no backend).
- **Reservations are taken ON THIS SITE**, not on Wix. `reservations.html` has a booking form POSTing to `/api/send` — hours-aware date/time picker, floor-plan capacity guard, confirmation email — landing in the admin's Reservations tab. `RESERVATION_BOOKING_URL` / `reservationUrl` still exists in `build.js` but the page renders no Wix button; do not describe reservations as "routed to Wix". Square Appointments was dropped 2026-06-27.
- **Inquiries carry a follow-up tracker** (`lib/orders/followup.js`): open / replied, plus a reminder date Erika sets for herself. Covers `contact` and `wholesale` ONLY — orders, classes and reservations have their own status flows, and the server refuses tracker actions on them. State lives in `details` (`responded_at`, `responded_note`, `reminder_date`, `reminder_note`); `/api/admin/orders` computes `followup` per row plus a `followupSummary`, so the browser never re-derives the date maths. Reminders are plain Edmonton dates, **in-admin only (no email)**, and a past date is refused. **None of the four actions send mail** — "replied" means she already wrote from her own inbox; `test/followup.test.js` spies on the send path and fails if one ever does.
- **Reservations can be paused mid-service** from the site manager (Reservations tab → Pause 30 min / 1 / 2 / 3 / 4 hours, or Resume now). `lib/orders/pause.js` owns it; its `OPTIONS` list is what both the buttons and the server validator read. State is a row in the Neon `site_settings` table, NOT `content.json` — that commits to GitHub and rebuilds, which is far too slow and could never un-pause itself. **It expires by being read**, so no cron can strand it. The Reserve page reads `GET /api/status` (public, cached 10s, so it can lag by that much) and swaps the form for a call-us notice; `api/send.js` refuses paused bookings anyway, since a tab opened before the pause knows nothing about it. Reads **fail open** like every other guard here. **Table bookings only** — classes and pickups keep running.
- **Pasta classes still use Square**, intentionally: Sunday Pasta Classes book + pay via a Square checkout form (`square.link/u/mTkWSnl5`) on the Experiences page; the Thursday drop-in books through FormSubmit and is **paid in person**.
- **Two class prices, and they are NOT the same.** Sunday (La Domenica) **$95/guest**; Thursday drop-in (Pasta With Erika) **$45/person** — free until 2026-09-15. Both normalise to type `'class'`, and `drop_in_date` is the ONLY thing separating the price, so drop-ins were long recorded at the Sunday rate. Amounts live in `lib/orders/submission.js` (`CLASS_PRICE_CENTS`, `DROP_IN_PRICE_CENTS`); `build-experiences.js` interpolates them into the copy — **never retype a price into the HTML**. `test/pricing.test.js` + `test/build-output.test.js` hold page, JSON-LD and till to the same constants.
- **Class dates are generated, never hand-kept.** Classes run **weekly on Sundays**; `lib/classes/schedule.js` is the single source of truth and emits the next `classWeeksShown` (default 5) Sundays, skipping the first Sunday of each month (closed) and any `classBlackoutDates`. The generator, `/api/class-availability`, the submit-time validator in `api/send.js` and the admin all read it — if they ever disagree a guest can book a date the server then rejects. All date math is UTC; only "today" is Edmonton-local.
- **Bookings carry two dates:** `class_date` (1st choice, required) and `class_date_2` (2nd choice, optional). If a Sunday falls below `classMin` (default 4 guests), Erika hits **Move to 2nd choices** in the admin's Pasta Classes tab: each booking goes to *its own* 2nd choice (they scatter — that is deliberate, nobody lands on a date they didn't pick), and anyone with no usable backup keeps their slot and is emailed to rebook. `lib/classes/push.js` decides, `api/admin/orders.js` (`action:'push_class'`) applies. Covered by `npm test`.
- **The white `.booking` card inside an olive/brown section** needs dark-on-light text explicitly — the section-level rules lighten form text for dark backgrounds and otherwise bleed in, which once rendered labels cream-on-white at 1.14:1. See the `.section--olive .booking …` overrides in `css/styles.css`; anything added to the section-level rules needs a counterpart there.
- **Menu page — every menu reads "Coming soon" and no PDF is linked** (client's call, 2026-09-15). The four PDFs are untouched in `/menus`. To bring one back: restore its `file`, flip `ready:true` in `menuCards` (`build.js`), rebuild. Intro copy, footnote and the menu FAQ answer (also in the FAQPage JSON-LD) all key off `MENUS_READY`; `test/build-output.test.js` fails if a PDF is linked while the page still says coming soon, or the reverse. Lunch = `lunch-menu.pdf`, Dessert = `dessert-menu.pdf` (drink + dessert).
- **One-off closures** (`closedDates`, `lib/cms/hours.js`) shut a SINGLE day for reservations *and* pickups. Not `hoursWed:'closed'`, which shuts every Wednesday — using that for "closed today" closes it forever. Embedded in both pickers at build time (`#service-hours`, `#pickup-hours`) and re-checked in `api/send.js`, since a page left open overnight carries yesterday's list. Past dates block nothing. **`2026-09-15` and `2026-09-21 | deep cleaning` are listed.**
- **Days with no online reservations** (`noReservationDates`, same file, same `date | reason` line format) block TABLE bookings only — the restaurant is open (buyout, private event), so pickups run and no closed banner shows. Embedded in `#service-hours` only (never `#pickup-hours`), re-checked in `api/send.js`. A day on both lists is a closure. Native date input, so the day can still be picked; the time list disables and says why.
- **A closure also shows a site-wide banner, and it takes itself down.** The pickers are the only place a closure used to be visible, so a guest reading the menu saw an open restaurant. Every page now carries `#site-closures` (the list + reasons) and a `#site-closure` bar. The bar is rendered by the build when the build ran on a closed day — so it holds with JS off — and `js/main.js` re-checks the same list against **Edmonton's** today on load, which is what clears it the next morning with no rebuild. On a closed day the announcement bar is hidden. A closure line may name its reason after a `|` or a spaced dash (`2026-09-21 | deep cleaning` → "closed today for deep cleaning"), which `api/send.js` repeats in its refusal. The reason lives on the date line **on purpose**: a standalone "closure reason" field outlives its day and retitles the next closure.
- **The site manager saves by committing `content.json` to GitHub**, so a token that can read but not write fails only at the last step — GitHub lets any token read a public repo. That was the live `403 Resource not accessible by personal access token`; the fix is **Contents: Read and write** on the repo for `GITHUB_TOKEN` in Vercel, not a code change. `lib/cms/store.js` maps each status to a sentence naming the fix (the raw API body goes to the log, never the screen), and `writeAccess()` answers "would a save land?" from the repo record so `/admin` warns on arrival instead of after she types the edit. Unknown is reported as unknown — a false alarm sends her chasing a healthy token. `test/cms-store.test.js` holds all of it.
- **A refused booking shows the server's reason, and past date pills remove themselves.** `api/send.js` answers a refusal with a sentence (`Only 4 seats left…`, `fully booked`, `closed that day`); the submit handler in `js/main.js` prints that sentence in `.form-error`, and falls back to the built-in "Something went wrong — call or email" only when the reply carries no reason (network failure). Before 2026-10-15 every refusal showed the generic line, which sent a guest with a fixable 5-on-4-seats booking off to email instead. The class/drop-in pills are baked at build time and the site only rebuilds on a push, so `main.js` also drops any pill dated before **Edmonton's** today on load (today stays — the server books it) and moves `required` to the next live pill. `test/build-output.test.js` pins both; a browser check against a stale copy of the live page is the real proof.
- **Operations layer (2026-10-18, branch `feature/ops-upgrade`).** `lib/orders/capacity.js` is the ONE seat pool — a class guest and a table reservation share a seat, so `api/send.js` caps a class by `min(classMax, room − reservations in the class window)` and a reservation by the room minus overlapping reservations AND the class (class window = CMS `classStart`/`classEnd`, default 5–9 PM; room = floor-plan seats or `totalCapacity`). **Class booking cutoff**: `classCutoffDaysBefore` (default 6 = the Monday before) closes a Sunday — `schedule.js` flags `closed` beside `full`, read by the pills, `/api/class-availability`, the submit-check and `main.js`. **Notifications**: `lib/notify/notifications.js` (bell) + `lib/notify/webpush.js` (VAPID); `dispatch.notify()` writes the bell row and pushes. `api/send.js` raises one per captured submission. **Admin** gains Alerts (bell + install/enable-push), Floor Status (tap Seat/Clear → `table_events`), Reports (covers / no-show rate / turns / class fill); reservation `no_show` action frees the seat. **Still 10/12 functions** — notify folded into `/api/admin/orders?sub=notify`, tables occupy/clear + reports into `/api/admin/reservations?sub=tables|reports`. **DB additions are all additive via `init()`** (ALTER…ADD COLUMN IF NOT EXISTS on `restaurant_tables`; new `table_events`, `notifications`, `push_subscriptions`) — no migration file, no DROP/TRUNCATE. **Web-push env**: `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` (secret) / `VAPID_SUBJECT` — the whole thing is inert if unset. Android Chrome installs the `/admin` PWA and gets push even when closed; iOS would need the PWA pinned first.
- **Pasta-shop DELIVERY by Uber Direct, one zone per day (2026-10-28, branch `feature/delivery-uber-direct`, proposal + demo in `ops\clients\dacecot\proposal-uber-direct\` and `work\demos\dacecot-delivery-demo`).** `lib/delivery/zones.js` (zone lines from CMS → zones/days/fee/cutoff, postal → zone, next delivery days on Edmonton's clock, `validateOrder`), `lib/delivery/uber.js` (OAuth client-credentials, quote → create delivery with `quote_id`, `getDelivery`; pure `buildQuoteRequest`/`buildDeliveryRequest` with Edmonton windows; `summarize` keeps `batch_id`/`dropoff_sequence_number`/status/tracking), `lib/delivery/day.js` (a day = its delivery orders; `canDispatch`, `runOf`, `week`). **Settings** are a CMS group `delivery` (`deliveryEnabled` default OFF → the page is pickup-only exactly as before; `deliveryZones` lines `Name | Day(s) | fee | FSAs`, empty = the proposal's starting map; cutoff hour; courier pickup time; customer window; min order). **Order flow:** the pasta-shop modal gains Pickup/Delivery (`#delivery-config` embedded at build, `js/main.js` shows the zone and the next three days); `api/send.js` re-validates every delivery order server-side (zone, day still open, fee from the zone, min order), stores `fulfillment/delivery_*` + `delivery_fee_cents` in details (`lib/orders/submission.js` adds the fee to `amount_cents`, and strips delivery keys from pickup orders), skips the product's fixed Square link and instead creates a Square checkout for the exact total when Square is configured AND the food price is known. **Kitchen:** admin → Delivery (`renderDelivery`, `?sub=delivery&week=`), per-order `delivery_pack`, `delivery_pack_day`, `delivery_dispatch` (refused until every bag is packed, once per day, and until `UBER_DIRECT_CLIENT_ID/SECRET/CUSTOMER_ID` are set; `UBER_DIRECT_SANDBOX=true` adds a robo-courier), `delivery_refresh`. Dispatch books ONE Uber delivery per order with the same pickup window (Uber batches them; there is no multi-stop request) and emails `sendDispatched` with the tracking link. **Still 10/12 functions** — no webhook; statuses are refreshed from the admin. `test/delivery.test.js` pins the cutoff on Edmonton time across DST, server-owned fees, Uber windows in MDT/MST, and the pack-before-dispatch gate. Go-live needs Erika's Uber Direct credentials on Vercel and `deliveryEnabled` on.
- **A Sunday class can be full without being cancelled.** `classBlackoutDates` REMOVES the date; `classFullDates` keeps it on the form, greyed out and labelled "Fully booked" (`schedule.js` flags `full:true`; `isBookable` refuses, `isFull` explains). Rendered sold out at BUILD time (holds with JS off), forced to zero seats in `/api/class-availability` (the live fetch cannot re-open it), refused again in `api/send.js`. **`Sunday, September 20, 2026` is marked full.**
